etcd 磁盘性能验证（K8s 集群部署前）#

etcd 的 Raft 协议要求每次写提案必须 fsync 到磁盘才能确认。磁盘慢会直接导致心跳超时、频繁选举、集群卡顿。

硬件要求#

项目 要求
磁盘类型 NVMe SSD 优先，SATA SSD 可接受
磁盘占用 独占一块盘，不与系统盘/日志盘共享
禁止使用 机械盘、NAS、SAN、iSCSI、Ceph RBD、NFS

小集群最低 50 顺序写 IOPS，大集群推荐 500+。

参考: https://etcd.io/docs/v3.6/op-guide/hardware/

部署前必测：WAL fsync p99 < 10ms#

这是唯一能在部署前用 fio 独立验证的硬指标。测不过不要上线。

测试命令#

fio --rw=write --ioengine=sync --fdatasync=1 \
    --directory=/var/lib/etcd \
    --size=22m --bs=2300 \
    --name=etcd-test

fio 版本需 >= 3.5（旧版不报 fdatasync 百分位）

参数说明：

  • --fdatasync=1 — 模拟 etcd 每次写 WAL 后 fsync 的行为，这是核心
  • --bs=2300 — 匹配 etcd WAL 条目典型大小（可用 strace -p $(pgrep etcd) -e write 确认实际值）
  • --directory — 必须指向 etcd 实际使用的存储路径
  • --size=22m — 产生约 10^4 个样本，保证 p99 统计可靠

结果判定#

看输出中 sync percentiles (usec) 段：

sync percentiles (usec):
| 99.00th =[ 2376]    ← 2.4ms，合格
| 99.50th =[ 9634]    ← 9.6ms，勉强
| 99.90th =[15795]    ← 15.8ms，p99.9 不看

99.00th < 10000 usec (10ms) 即通过。

注意：fio 是隔离测试，实际 etcd 还有额外 I/O。fio 测出接近 10ms 说明余量不够，建议换更快的盘。

参考: https://web.archive.org/web/20230930053243/https://prog.world/is-storage-speed-suitable-for-etcd-ask-fio/

部署后监控指标#

WAL fsync 达标上线后，还需持续关注以下指标：

指标 目标 说明
etcd_disk_wal_fsync_duration_seconds p99 < 10ms 同部署前指标，运行态验证
etcd_disk_backend_commit_duration_seconds p99 < 25ms boltdb 刷盘延迟，无法部署前测试
etcd_server_leader_changes_seen_total 0 频繁切换说明磁盘/网络有问题
etcd_disk_wal_write_duration_seconds p99 < 10ms v3.6+ 新增，覆盖 write() 系统调用延迟

PromQL 示例：

histogram_quantile(0.99, rate(etcd_disk_wal_fsync_duration_seconds_bucket[5m]))
histogram_quantile(0.99, rate(etcd_disk_backend_commit_duration_seconds_bucket[5m]))
increase(etcd_server_leader_changes_seen_total[15m])

参考: https://etcd.io/docs/v3.6/op-guide/monitoring/

官方告警阈值#

告警 条件 持续
etcdHighFsyncDurations (warning) WAL fsync p99 > 500ms 10m
etcdHighFsyncDurations (critical) WAL fsync p99 > 1s 10m
etcdHighCommitDurations (warning) Backend commit p99 > 250ms 10m
etcdNoLeader (critical) 无 leader 1m
etcdHighNumberOfLeaderChanges (warning) >= 4次/15min 5m

注意：告警阈值远高于运行目标（500ms vs 10ms），告警触发时集群已严重劣化。

常见问题#

Q: fio 测试通过但 etcd 运行后 WAL fsync 仍然高？

检查同节点是否有 I/O 竞争。控制平面节点不应跑 I/O 密集型负载。可用 ionice -c2 -n0 -p $(pgrep etcd) 提升 etcd 优先级。

Q: WAL fsync 正常但集群仍不稳定？

可能是 write() 系统调用本身慢（内核 bug），v3.6+ 查看 etcd_disk_wal_write_duration_seconds。案例: https://github.com/etcd-io/etcd/issues/17615

Q: 跨机房部署？

默认 heartbeat-interval=100ms、election-timeout=1000ms，跨机房需适当增大。

附录 A：为什么磁盘性能对 etcd 至关重要#

etcd 使用 Raft 共识协议保证分布式一致性，其核心流程是：

  1. 客户端发起写请求
  2. Leader 将提案写入本地 WAL (Write-Ahead Log)
  3. Leader 调用 fsync 将 WAL 持久化到磁盘
  4. Leader 将提案发送给 Followers
  5. 多数成员确认后，Leader 提交提案并响应客户端

关键点：步骤 3 的 fsync 是同步阻塞操作，每次写请求都必须等待磁盘确认。集群中多数成员都要完成这个过程。

因此磁盘延迟直接影响：

  • WAL fsync 慢 → 写请求响应慢 → API Server 卡顿 → 整个 K8s 控制面变慢
  • WAL fsync 超过心跳间隔 → Follower 认为 Leader 失效 → 触发重新选举 → 集群短暂不可用
  • 频繁选举 → 提案堆积 → 雪崩式劣化

此外，etcd 还使用 boltdb (B+树) 存储数据快照，定期将内存中的变更提交到磁盘（backend commit）。这部分是周期性批量操作，延迟要求略低于 WAL fsync（25ms vs 10ms），但同样不可忽视。

还有一个容易被忽略的环节：WAL 写入的 write() 系统调用本身（不包含 fsync）。在 etcd v3.6 之前没有专门监控这个指标，导致出现过 WAL fsync 正常但 write() 因内核 bug 而极慢的案例（etcd#17615）。v3.6+ 新增了 etcd_disk_wal_write_duration_seconds 指标来覆盖这个盲区。

参考: https://etcd.io/docs/v3.6/op-guide/performance/
