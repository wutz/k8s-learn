kubespray-v2.28.0 Control Plane 节点扩容方案#

背景#

  • 现有 1 个 Control Plane 节点：mn-192-168-3-21
  • Kubespray 版本：2.28.0

目标#

  • 新增 2 个 Control Plane 节点：mn-192-168-3-22、mn-192-168-3-23

⚠️ 实现高可用（HA）控制平面，确保 etcd 集群扩展以支持奇数个成员（从 1 个扩展到 3 个）。

前置条件#

  • 新节点（mn-192-168-3-22 和 mn-192-168-3-23）已准备好：
    • 安装兼容的操作系统（例如 Ubuntu 或 CentOS），并配置网络、SSH 无密码访问（从 Ansible 控制机）
    • 确保 Ansible 可以连接到新节点（测试 ansible -i inventory/mycluster/inventory.ini all -m ping）
    • 节点硬件满足 Kubernetes Control Plane 要求（至少 2 GB 内存、2 CPU 核心）
  • 备份现有集群状态，包括 etcd 数据（使用 etcdctl snapshot save）
  • 参考 Kubespray 官方文档：Recovering the control plane

注意：Kubespray 使用 recover-control-plane.yml playbook 来处理 Control Plane 扩展，因为直接使用 scale.yml 可能导致 etcd 配置问题。将新节点模拟为"broken"节点来添加它们，从而安全更新 etcd 成员。

扩容步骤#

1. 配置 Inventory 文件#

更新 inventory/mycluster/inventory.ini 文件，将新节点添加到 [kube_control_plane] 和 [etcd] 组中。同时，定义 [broken_etcd] 和 [broken_kube_control_plane] 组，将新节点视为"broken"以触发恢复逻辑。

示例配置：

[kube_control_plane]
mn-192-168-3-21 ansible_host=192.168.3.21 etcd_member_name=etcd1
mn-192-168-3-22 ansible_host=192.168.3.22 etcd_member_name=etcd2
mn-192-168-3-23 ansible_host=192.168.3.23 etcd_member_name=etcd3

[etcd:children]
kube_control_plane

[broken_etcd]
mn-192-168-3-22 ansible_host=192.168.3.22 etcd_member_name=etcd2
mn-192-168-3-23 ansible_host=192.168.3.23 etcd_member_name=etcd3

[broken_kube_control_plane]
mn-192-168-3-22 ansible_host=192.168.3.22
mn-192-168-3-23 ansible_host=192.168.3.23

解释：etcd_member_name 必须唯一，用于 etcd 集群成员标识。[broken_*] 组用于 playbook 模拟恢复场景，从而添加新 etcd 成员而不破坏现有集群。

2. 修改 etcd 配置（如果必要）#

在 Kubespray 2.28.0 中存在 etcd 配置 bug，导致 etcd.env 和 etcd-events.env 中的 ETCD_INITIAL_CLUSTER 配置包含多余引号，可能导致 etcd 启动失败。

  • 参考修复：Kubespray PR #12350 Commit

3. 更新 Ansible Facts#

运行以下命令刷新节点 facts：

ansible-playbook -i inventory/mycluster/inventory.ini --become --become-user=root playbooks/facts.yml

解释：这确保 Ansible 收集新节点的最新信息，用于后续 playbook。

4. 执行扩容#

使用 recover-control-plane.yml playbook 添加新节点：

ansible-playbook -i inventory/mycluster/inventory.ini --become --become-user=root recover-control-plane.yml --limit=etcd,kube_control_plane -v -e etcd_retries=10

解释：

  • --limit=etcd,kube_control_plane：限制 playbook 只影响 etcd 和 Control Plane 节点
  • -v：启用详细输出，便于调试
  • -e etcd_retries=10：增加 etcd 操作重试次数，以处理潜在的网络或同步问题

注意：如果 playbook 失败，检查日志并确保新节点可达。可能需要设置 -e ignore_assert_errors=yes 来忽略某些断言错误。

5. 清理 Inventory#

扩容成功后，从 inventory.ini 中移除 [broken_etcd] 和 [broken_kube_control_plane] 组，以避免未来 playbook 误操作。

检查验证#

检查节点状态#

kubectl get nodes

预期输出：

NAME              STATUS   ROLES           AGE    VERSION
mn-192-168-3-21   Ready    control-plane   18m    v1.32.5
mn-192-168-3-22   Ready    control-plane   4m5s   v1.32.5
mn-192-168-3-23   Ready    control-plane   4m3s   v1.32.5

检查 etcd 集群健康#

etcdctl --endpoints=https://127.0.0.1:2379 --cacert=/etc/ssl/etcd/ssl/ca.pem --cert=/etc/ssl/etcd/ssl/node-$(hostname).pem --key=/etc/ssl/etcd/ssl/node-$(hostname)-key.pem member list

预期输出：

9f387ea04d3b1f4e, started, etcd2, https://192.168.3.22:2380, https://192.168.3.22:2379, false
c2ad425db0cdd901, started, etcd3, https://192.168.3.23:2380, https://192.168.3.23:2379, false
c50216e882985073, started, etcd1, https://192.168.3.21:2380, https://192.168.3.21:2379, false

解释：每个成员包括 ID、状态、名称、对等 URL 和客户端 URL。最后的 "false" 表示非 learner 模式。确保所有成员在线，无 unstarted 或 unhealthy 节点。

检查 Control Plane 组件#

kubectl get pods -n kube-system

确保 kube-apiserver、kube-controller-manager、kube-scheduler 等 Pod 在新节点上运行。

监控日志#

使用 journalctl -u kubelet 或 kubectl logs 检查任何错误。

潜在问题与排查#

  • etcd 同步失败：增加 etcd_retries 或检查网络连通性（端口 2379、2380）
  • 证书问题：确保新节点的证书正确生成（playbook 会处理，但可手动验证 /etc/kubernetes/ssl）
  • 版本不匹配：确认所有节点 Kubernetes 版本一致（v1.32.5）
  • 如果 playbook 失败于 etcd 配置，参考上述手动修复
