二、Kubespray 变更#

2.1 破坏性变更#

2.1.1 ingress-nginx addon 被移除#

Kubespray 移除范围 (PR #12767):

删除了整个 roles/kubernetes-apps/ingress_controller/ingress_nginx/ 子角色，包括：

  • defaults/main.yml（变量定义: ingress_nginx_enabled、镜像版本等）
  • tasks/main.yml（部署任务）
  • 17 个 Jinja2 模板（Namespace、RBAC、ConfigMap、Deployment、Service、IngressClass、Admission Webhook 等）
  • docs/ingress/ingress_nginx.md 文档
  • ingress_nginx_enabled 变量引用（addons.yml、download.yml、main.yml）
  • 共 33 个文件变更，删除 1034 行，仅新增 12 行

上游归档经过:

时间 事件
2025-11-11 SIG Network + 安全委员会发布官方博客宣布退役
2026-03-24 kubernetes/ingress-nginx 仓库正式归档（19.5k stars, 8432 commits）
2026-03-24 替代方案 InGate (kubernetes-sigs/ingate) 也同步归档（仅 49 commits）

根因: 长期仅 1-2 人业余维护；snippets 注入等"灵活性"特性成为不可偿还的安全债务。

替代方案（按集群现状选择）:

方案 Ingress v1 兼容 适用场景
Istio Ingressgateway（已部署 Istio 时） 是 已有 Istio 的集群
Gateway API（官方推荐方向） 否，需重写为 HTTPRoute 新项目、长期规划
Traefik IngressController 是 无服务网格需求
HAProxy Ingress 是 无服务网格需求
Envoy Gateway 否 需要 Envoy 但不需要 Istio

Istio Ingressgateway 作为过渡方案的注意事项:

Istio ingressgateway 可作为过渡方案承接 Kubernetes Ingress v1 API，但不能假设现有 Ingress 只需切换 ingressClassName 即可无缝迁移。官方更推荐长期迁移到 Gateway API，且需要逐项核对 path 匹配语义、TLS Secret 所在 namespace，以及 nginx annotation 的等价配置。

  1. 创建 IngressClass:
apiVersion: networking.k8s.io/v1
kind: IngressClass
metadata:
  name: istio
spec:
  controller: istio.io/ingress-controller

  1. 对结构简单的 Ingress，建议先在非生产环境验证 ingressClassName: nginx → ingressClassName: istio

  2. 对 nginx 专属 annotation，需迁移到 Istio 原生配置或 Gateway API 对应能力，并逐条验证行为一致性

nginx annotation → Istio 映射:

nginx Annotation Istio 替代
nginx.ingress.kubernetes.io/rewrite-target VirtualService rewrite 或 HTTPRoute filter
nginx.ingress.kubernetes.io/ssl-redirect Gateway TLS 配置或 VirtualService redirect
nginx.ingress.kubernetes.io/proxy-body-size 通常需 EnvoyFilter 或网关/代理层专门配置
nginx.ingress.kubernetes.io/auth-type RequestAuthentication / AuthorizationPolicy
nginx.ingress.kubernetes.io/cors-* VirtualService corsPolicy
nginx.ingress.kubernetes.io/canary VirtualService 流量权重分配
nginx.ingress.kubernetes.io/custom-snippets EnvoyFilter（需更多专业知识）

长期建议: 渐进迁移到 Gateway API（Gateway + HTTPRoute）。Kubespray v2.31.0 的 addons.yml 中有 gateway_api_enabled: false，设为 true 可安装 Gateway API CRDs（仅安装 CRDs，不包含具体网关控制器）。

注意: 现有部署不会立刻中断，Helm chart 和容器镜像仍然可用，但不再有安全修复。

2.1.3 废弃变量自动检测#

新增自动化验证角色 (PR #12942)

在 validate_inventory 角色中新增 "Fail if removed variables are used" 任务，作为 playbook 启动前的第一道 inventory 检查。

要点:

  • 使用 Ansible query('varnames', ...) 检查 inventory/extra-vars 中是否定义了已移除变量
  • run_once: true，每个 play 只执行一次
  • 不依赖 gathered facts，只检查变量定义
  • 当前正则写法为 ^var1|var2$，严格说不是精确匹配；但 v2.31.0 仅检查 1 个变量，当前不会造成误判

v2.31.0 当前检测列表:

已移除变量 移除版本 说明
kubelet_static_pod_path 2.31.0 开发周期内引入后即移除，不再存在

如果检测到已移除变量: playbook 立即中止，必须在 inventory 中清理该变量后才能继续运行。

来源: PR #12942 | Issue #11039

原变量名同时包含拼写错误 confing 和多余双下划线 __，现统一修正为 ssh_bastion_config_name。

影响评估:

3.2 Kubernetes 1.34.3 → 1.35.4 重要变更#

cgroup v1 默认拒绝启动#

影响等级: ⚠️ 最高 — 升级后 kubelet 可能无法启动

两阶段演进:

阶段 K8s 版本 KEP 行为
维护模式 v1.31 KEP-4569 引入 FailCgroupV1 字段，默认 false，仅打警告
废弃 v1.35 (Beta) KEP-5573 FailCgroupV1 默认改为 true，kubelet 拒绝启动
移除 (计划) ≥ v1.38 — 完全删除 cgroup v1 代码

Kubespray 应对:

  • 新增变量 kubelet_fail_cgroup_v1: true（默认）
  • 写入 kubelet-config 模板，仅对 K8s ≥1.35 生效
  • 涉及模板:
    • roles/kubernetes/control-plane/templates/kubeadm-config.v1beta4.yaml.j2
    • roles/kubernetes/node/templates/kubelet-config.v1beta1.yaml.j2

影响: 升级到 v1.35 后，cgroup v1 节点的 kubelet 直接启动失败。

常见场景：Ubuntu 22.04 集群

  • Ubuntu 22.04 默认使用 cgroup v2，标准安装情况下不会因 FailCgroupV1=true 导致 kubelet 启动失败
  • 只需确认节点未被手动切回 cgroup v1，例如 GRUB 中存在 systemd.unified_cgroup_hierarchy=0

验证方法:

# 1. 确认当前 cgroup 版本
stat -fc %T /sys/fs/cgroup
# cgroup2fs = v2（正常，无需操作）
# tmpfs    = v1（需排查是否手动降级，需移除 GRUB 中的 =0 参数后重启）

# 2. 检查 GRUB 是否被手动设置为 cgroup v1
grep -rE "unified_cgroup_hierarchy" /etc/default/grub /etc/default/grub.d/*.cfg 2>/dev/null
# 无输出 = 默认 cgroup v2（正常）
# 有 =0  = 曾被手动降级（需移除）

# 3. 确认 containerd cgroup driver
containerd config dump | grep -A5 "plugins.*cgroup"
# 或查看运行时配置
ctr --address /run/containerd/containerd.sock info | grep -i cgroup

containerd cgroup driver 注意事项:

  • cgroup v2 下推荐使用 systemd driver
  • Kubespray 默认已为 containerd 配置 systemd driver
  • 如发现 kubelet 与 containerd 的 driver 混用，建议统一为 systemd

如确实需要从 cgroup v1 迁移到 v2（仅限被手动降级的节点）:

# 1. 移除 GRUB 中的 cgroup v1 强制参数
sudo vi /etc/default/grub
# 删除 GRUB_CMDLINE_LINUX 中的 systemd.unified_cgroup_hierarchy=0

# 2. 更新 GRUB 并重启
sudo update-grub && sudo reboot

# 3. 重启后验证
stat -fc %T /sys/fs/cgroup  # 期望: cgroup2fs

工作负载兼容性（cgroup v2 环境下需注意）:

  • OpenJDK: 需 8u372+ / 11.0.16+ / 17+（旧版无法正确读取 cgroup v2 内存限制）
  • Node.js: 需 20.3.0+
  • Go 应用 (uber-go/automaxprocs): 需 v1.5.1+
  • cAdvisor: 需 >= v0.43.0
  • OOM 行为: cgroup v2 默认杀整个 cgroup（oom.group），可设 singleProcessOOMKill: true 回退到 v1 行为

操作系统 cgroup 默认版本对照:

系统 默认 cgroup 备注
Ubuntu 22.04 (Jammy) v2 systemd 249，编译时 -Ddefault-hierarchy=unified
Ubuntu 24.04 (Noble) v2 systemd 255
RHEL 8 v1
RHEL 9 v2 RHEL 10 不再支持 cgroup v1

3.3 etcd 3.5.26 → 3.6.10 重要变更#

这是本轮升级中风险最高的组件变更之一。

破坏性变更#

变更 影响
存储格式变更 bbolt v2 后端改进；回退需遵循官方 downgrade 流程或从升级前 snapshot 恢复
gRPC proxy 重构 部分标志名变更
已废弃的 v2 API 完全移除 依赖旧 v2 API 的工具将失败
认证模型调整 RBAC 部分边界情况行为变化
etcdctl 部分废弃标志移除 旧版 snapshot status 标志等

升级路径（强制）#

etcd 3.5.x (< 3.5.26)  →  etcd 3.5.26+  →  etcd 3.6.10
         ⚠️ 必须先升到 3.5.26+      ⚠️ 回退需按官方流程执行

为什么必须先升到 3.5.26+？

官方升级文档明确要求：所有 3.5 member 必须先升级到 3.5.26+，因为 3.5.24 到 3.5.26 修复了多个可能阻塞 3.6 升级的问题。

  1. 升级方式是滚动升级，逐个 member 从 3.5.26 升到 3.6，过渡期允许 3.5.26 与 3.6 共存
  2. 不应依赖“直接替换二进制”回滚；如需回退，需按官方 downgrade 流程执行，或从升级前备份恢复

Kubespray 实操: 先升级到 2.30.0（etcd 3.5.26），确认集群健康后再升级到 2.31.0。

新特性与改进#

类别 说明
结构化日志 从 capnslog 迁移到 slog，支持 JSON 输出
在线碎片整理改进 降低对在线集群的影响
Watch 性能优化 减少大集群 watch 路径的内存分配
MVCC 读锁争用降低 BoltDB 后端 range 查询更快

升级前检查#

# 1. 确认当前 etcd 版本
etcdctl version

# 2. 确认集群健康
etcdctl endpoint health --cluster

# 3. 备份！
etcdctl snapshot save /backup/pre-3.6-$(date +%Y%m%d).db

# 4. 性能基线检查（非 v3.6 新功能，但建议升级前运行）
etcdctl check perf

3.4 containerd 2.2.1 → 2.2.3 & runc 1.3.4 → 1.4.2#

containerd 2.2.1 → 2.2.3: 补丁级升级，无破坏性变更。

containerd 1.x→2.x 的跨版本变更已在更早 Kubespray 版本完成；本轮 2.2.1→2.2.3 不涉及新的配置格式变化。

runc 1.3.4 → 1.4.2: 小版本升级，向后兼容，风险低。

runc 1.4.x 主要是功能补充和回归修复，重点包括 cgroup v2 支持改进、安全加固，以及若干容器生命周期相关修复。建议先在非生产环境验证 cgroup v2 下容器创建/销毁行为。

四、通用升级检查清单#

适用于使用 Kubespray 从 v2.30 升级到 v2.31 的集群；以下项目按命中条件执行。

4.1 升级前必做#

  • cgroup 版本确认 — 见三.2
    • stat -fc %T /sys/fs/cgroup → 期望 cgroup2fs
    • 如输出 tmpfs: 检查 GRUB 是否有 systemd.unified_cgroup_hierarchy=0，移除后 update-grub → 重启
  • containerd cgroup driver 确认（如运行时为 containerd） — 见三.2
    • Kubespray 部署默认 systemd driver，检查是否有手动改过
  • etcd 分步升级（如使用 Kubespray 管理的 etcd） — 见三.3
    • 先升到 2.30.0 (etcd 3.5.26)，再升 2.31.0 (etcd 3.6.10)
    • 升级前必须备份: etcdctl snapshot save
    • 确认集群健康: etcdctl endpoint health --cluster
    • 如需回退，需按官方 downgrade 流程执行，或从升级前 snapshot 恢复
  • 移除 --pod-infra-container-image kubelet 标志（如非 kubeadm 集群，或曾手动追加该参数） — 见三.2
    • 检查所有节点 kubelet 启动参数，删除此标志
  • 评估 IPVS kube-proxy 迁移（如当前 kube_proxy_mode: ipvs） — 见三.2
    • 本次升级后至少会出现废弃告警，建议评估迁移到 nftables
  • 检查 StorageVersionMigration v1alpha1 资源 — 见三.2
    • kubectl get storageversionmigrations --all-namespaces
    • 如存在: kubectl delete storageversionmigrations --all -A
  • ingress-nginx 迁移（如当前仍在使用该 addon） — 见二.1.1
    • 如当前在用，需提前规划迁移（Istio / Gateway API / 第三方控制器）
  • Dashboard 替换（如当前仍依赖 Dashboard） — 见二.1.2
    • 如需 Web UI，部署 Headlamp；移除 dashboard_enabled 变量
  • 清理废弃变量 — 见二.1.3
    • 检查 inventory 中是否定义了 kubelet_static_pod_path，如有则删除
  • bastion 变量重命名（如曾覆盖旧变量名） — 见二.1.4
    • 如 inventory 中覆盖过 ssh_bastion_confing__name，改为 ssh_bastion_config_name
  • 自定义控制器 gogo/protobuf 依赖检查（如集群中存在自研或第三方控制器） — 见三.2
    • 检查自研/第三方控制器是否依赖 ProtoMessage() 方法

4.2 升级后验证#

  • 工作负载 cgroup v2 兼容性（如节点使用或将迁移到 cgroup v2） — 见三.2
    • OpenJDK: 8u372+ / 11.0.16+ / 17+
    • Node.js: 20.3.0+
    • Go 应用 (uber-go/automaxprocs): v1.5.1+
  • 第三方 Agent cgroup v2 兼容: cAdvisor >= v0.43.0
  • OOM 行为: cgroup v2 默认杀整个 cgroup，如需单进程 OOM kill 需配 singleProcessOOMKill: true

4.3 长期规划#

  • cgroup v1 完全移除准备: K8s v1.38 计划删除 cgroup v1 代码
    • 届时 kubelet_fail_cgroup_v1: false 将不再有效
  • IPVS kube-proxy 迁移（如当前使用 IPVS）: v1.35 已废弃，逐步迁移到 nftables
  • Gateway API 迁移: Ingress → Gateway API 是 Kubernetes 网络发展方向
