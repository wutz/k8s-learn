Kubernetes 批处理调度指南与选型决策#

适用环境：Kubernetes v1.32+，Kubeflow Trainer 场景 核心目标：解决分布式训练的 Gang Scheduling（全组 Pod 必须同时启动）与资源配额管理问题。

1. 结论与架构推荐（TL;DR）#

针对当前生产环境和一线实操需求，经过对多个调度方案的深度对比与实测，给出以下明确的选型结论：

  • 🏆 首选方案：Kueue
    • 核心优势：在准入层进行管控，资源不够时完全不创建 Pod，零额外调度开销。对 Kubeflow Trainer 具备完美的原生支持（仅需增加 3 个字段，全程自动化）。
    • 适用场景：绝大多数 AI 训练场景、需要精准配额控制、追求系统轻量稳定的集群。
  • 🥈 备选方案：Volcano
    • 核心优势：老牌批处理调度器，在调度层工作。插件生态丰富。
    • 适用场景：极大规模纯 GPU 集群、重度多租户、需要复杂的调度策略（如 DRF、Binpack、比例分配）。
  • 🚫 明确弃用：Coscheduling (scheduler-plugins)
    • 原因：设计缺陷导致在资源不足时会引发爆发式的 FailedScheduling 事件（实测产生 40 万+ 事件），极度消耗 apiserver 和调度器性能。社区重心已转移，长期维护存疑。
  • 🚫 当前不可用：kube-scheduler 原生 Gang Scheduling
    • 原因：原生支持（v1.35+）目前仍处于 Alpha 阶段，默认禁用，禁止用于生产环境。待未来稳定后可作为演进方向。

🔥 致命冲突警告：Kueue 与 Volcano 共存的 Webhook 陷阱 如果集群中同时安装了 Kueue 和 Volcano，Kueue 的 Pod mutating webhook 会拦截 Volcano 的 Pod，强行覆盖 schedulerName 并注入 suspended=true，导致 Volcano 调度彻底瘫痪。 规避方案：确保 Kueue 的 values.yaml 中 integrations.frameworks 列表绝对不要包含 pod 和 deployment，只保留 batch/job, trainer.kubeflow.org/trainjob 等明确的 Job 资源。

2. 核心场景实战操作#

在确定选型后，以下是一线工程师最常用的 TrainJob 提交流程和配置模板。

场景 A：使用 Kueue 提交 TrainJob（推荐，极简）#

Kueue 的接入体验最好，无需手动创建任何额外的 PodGroup 资源，依靠 webhook 自动接管。

apiVersion: trainer.kubeflow.org/v1alpha1
kind: TrainJob
metadata:
  name: my-job
  labels:
    kueue.x-k8s.io/queue-name: gpu-local-queue       # 必填：指向对应的 LocalQueue
    # kueue.x-k8s.io/priority-class: high-priority   # 可选：指定 Workload 优先级
spec:
  suspend: true                                      # 必填：设为 true，交由 Kueue 决定何时 unsuspend
  runtimeRef:
    name: torch-distributed
  trainer:
    numNodes: 2
    resourcesPerNode:
      requests:
        nvidia.com/gpu: "1"

避坑：不要配置 spec.managedBy，该字段仅在 MultiKueue 跨集群场景使用。

场景 B：使用 Volcano 提交 TrainJob（繁琐，易错）#

Volcano 需要依赖 PodGroup 对象，但 TrainJob 的 webhook 不会自动创建 Volcano 版本的 PodGroup。

⚠️ 时序陷阱：必须先手动创建 PodGroup，再提交 TrainJob，否则任务永远无法被调度。

# 1. 必须先创建 PodGroup
apiVersion: scheduling.volcano.sh/v1beta1
kind: PodGroup
metadata:
  name: my-training
spec:
  minMember: 2          # 必须等于 TrainJob.trainer.numNodes
  queue: default
---
# 2. 再提交 TrainJob
apiVersion: trainer.kubeflow.org/v1alpha1
kind: TrainJob
metadata:
  name: my-training
spec:
  suspend: false
  runtimeRef:
    name: torch-distributed-volcano # 此 runtime 需配置 schedulerName: volcano
  trainer:
    numNodes: 2
    resourcesPerNode:
      requests: { nvidia.com/gpu: "1" }
  runtimePatches:
    - manager: scheduling.volcano.sh/volcano
      trainingRuntimeSpec:
        template:
          spec:
            replicatedJobs:
              - name: node
                template:
                  spec:
                    template:
                      metadata:
                        annotations:
                          scheduling.k8s.io/group-name: my-training # 必须与上方 PodGroup 名字一致

3. 核心差异对比：Kueue vs Volcano#

我们剔除不再推荐的方案，仅对比生产可用的两套系统，帮助您理解它们的行为差异。

维度 🥇 Kueue 🥈 Volcano
切入层面 准入层（Admission Webhook） 调度层（独立 scheduler）
工作原理 资源够 → 放行 (unsuspend) 创建 Pod。
资源不够 → 拦截，保持 Job suspend，0 个 Pod 被创建。		 Pod 直接创建 → 绕过原生调度器交由 Volcano 评估。
资源不够 → 全组 Pod 处于 Pending 状态，等待凑齐。
队列/配额发现 需手工填写 nominalQuota，不自动发现集群资源（运维需手动对齐容量）。 默认 root Queue 自动继承集群总资源。
CRD 冲突注意 LocalQueue 的 short name 是 queue ⚠️ Queue 的 short name 是 q ⚠️
抢占粒度 跨同 Cohort 的 Workload 级抢占（all-or-nothing）。 跨 Queue / 同 Queue 的 PodGroup 级抢占。
额外组件数 1 个：kueue-controller-manager 3 个：scheduler + controller + admission

5. 附录与技术前瞻#

本节内容供架构师或资深工程师参考，解答“为什么不用 XXX”以及“Kubernetes 原生未来怎么做”。

5.1 为什么坚决淘汰 Coscheduling？#

Coscheduling 作为 scheduler-plugins 的一部分，最大的硬伤在于资源不足时的调度风暴。 它作为一个“插件”，底层仍然依赖 kube-scheduler 逐个 Pod 进行处理。当提交一个需要 48 GPU 的任务，但集群只有 24 GPU 时： 所有 48 个 Pod 都会被创建并处于 Pending -> 调度器在每一个调度周期 (Scheduling Cycle) 都会傻乎乎地去尝试绑定这 48 个 Pod -> 到了 Permit 阶段发现凑不齐，全部打回 -> 下个周期继续尝试。 实测结果：在很短的时间内就会产生超过 40万次 的 FailedScheduling 事件，极大地消耗控制面资源。

5.2 Kubernetes 原生 Gang Scheduling 演进 (v1.35 / v1.36)#

SIG-scheduling 的最终形态其实是 Kueue 负责配额管理 + Kube-Scheduler 原生负责 Gang 调度。 目前原生支持在 v1.35 Alpha 引入，它的核心架构设计如下：

  1. API 解耦 (v1.36 v1alpha2)：将策略模板 Workload 与运行时实例 PodGroup 完全解耦，解决了单个对象过大带来的 etcd 压力。
  2. PreEnqueue 阻塞：引入新的扩展点。Pod 在进入调度队列前，必须确认关联的 PodGroup 已存在，且已创建的 Pod 数量 ≥ minCount，否则直接拦截在队外，避免 Coscheduling 那种盲目重试。
  3. Workload Scheduling Cycle (v1.36)：这是最大的架构改变。以前是逐个 Pod 调度，现在是将整个 PodGroup 作为一个调度单元，在单次周期内完成全组评估，彻底解决死锁和活锁问题。
  4. Delayed Preemption (延迟抢占)：在寻找受害者 (victims) 时只计算不执行。只有当确认抢占后能满足整个 PodGroup 的 minCount 时，才会真正执行驱逐。实现了零无效干扰。

演进路线图：

  • 当前：Kueue 为主。
  • 未来 (待原生稳定)：Kueue + 原生 PodGroup。Kueue 释放 Pod 后，交由原生内置机制保证 All-or-nothing。彻底告别第三方调度器组件。
