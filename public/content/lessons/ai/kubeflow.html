Kubeflow#

Kubeflow 是基于 Kubernetes 的开源 AI/ML 平台，为构建端到端的 AI 平台提供基础工具集。它由多个子项目组成，覆盖 AI 生命周期的各个阶段，包括数据处理、模型训练、调优、管道编排和模型服务等。

前置准备（必做）#

  • K8s 版本：查 release notes 匹配（当前支持 1.35/1.36+）。
  • 内核调优（所有节点）：
sudo sysctl fs.inotify.max_user_instances=2280
sudo sysctl fs.inotify.max_user_watches=1255360
  • GPU：安装 GPU Operator，label/taint GPU 节点。
  • Storage：高性能 StorageClass（必须准备一个default sc） + S3 兼容对象存储（kubeflow 默认使用 SeaweedFS，在pipeline章节默认自动安装）。
  • 节点资源（infra 控制面节点）：Kubeflow 控制面组件（含 Istio/Knative/认证/证书等依赖）requests 总量约 5.3核 CPU / 10.8Gi 内存。单节点最低 8核/16Gi，推荐 16核/32Gi。
  • 工具：kubectl、kustomize（最新）。

离线 vendor 化（按需执行）#

部分组件直接引用 GitHub URL，离线/内网环境的 kustomize build 会失败。下面按组件独立列出，只需为你计划安装的组件执行对应章节：

  • Pipeline 组件 vendor (argo-workflows v3.7.3)：仅安装 Kubeflow Pipelines 时执行
  • Trainer 组件 vendor (jobset v0.10.1)：仅安装 Trainer (training operator v2) 时执行

如果你的部署节点能直接访问 GitHub（如有出网代理），可以跳过本章节。

Pipeline 组件 vendor (argo-workflows v3.7.3)#

applications/pipeline/upstream/third-party/argo/ 下若干 kustomization.yaml 直接引用了 GitHub URL（https://github.com/argoproj/argo-workflows/...?ref=v3.7.3）。每次 kustomize build 都会触发 git fetch，离线/内网受限环境会失败：

error: accumulating resources: ...
Get "https://github.com/argoproj/argo-workflows/manifests/base/crds/minimal?ref=v3.7.3": dial tcp ...: connection timed out

修复思路：在一台能访问 GitHub 的机器上把 argo-workflows v3.7.3 manifests 拉下来 vendor 到本仓库，把 kustomization 改成引用本地路径。这一步是一次性工作，做完后随仓库一起提交，后续部署不再需要外网。

步骤 1：在能访问 GitHub 的机器上下载 manifests#

git clone --depth=1 -b v3.7.3 https://github.com/argoproj/argo-workflows.git /tmp/argo-workflows

将下面四个目录打包，传到部署服务器：

cd /tmp/argo-workflows
tar czf /tmp/argo-v3.7.3-manifests.tar.gz \
  manifests/base/crds/minimal \
  manifests/base/workflow-controller \
  manifests/cluster-install-no-crds/workflow-controller-rbac \
  manifests/namespace-install/workflow-controller-rbac

# 上传到部署服务器（示例）
scp /tmp/argo-v3.7.3-manifests.tar.gz <user>@<master>:/tmp/

步骤 2：将 manifests vendor 到仓库#

在仓库根目录（即 community-distribution-26.03/）下执行：

cd ai/kubeflow/community-distribution/community-distribution-26.03

# 创建 vendor 目录
VENDOR=applications/pipeline/upstream/third-party/argo/vendor
mkdir -p $VENDOR

# 解压 manifests 到 vendor 目录
tar xzf /tmp/argo-v3.7.3-manifests.tar.gz -C /tmp/
cp -r /tmp/manifests/base/crds/minimal                                $VENDOR/crds-minimal
cp -r /tmp/manifests/base/workflow-controller                         $VENDOR/workflow-controller
cp -r /tmp/manifests/cluster-install-no-crds/workflow-controller-rbac $VENDOR/workflow-controller-rbac-cluster
cp -r /tmp/manifests/namespace-install/workflow-controller-rbac       $VENDOR/workflow-controller-rbac-namespace

# 验证结构（每个目录里都应有自己的 kustomization.yaml）
find $VENDOR -name kustomization.yaml

预期输出：

applications/pipeline/upstream/third-party/argo/vendor/crds-minimal/kustomization.yaml
applications/pipeline/upstream/third-party/argo/vendor/workflow-controller/kustomization.yaml
applications/pipeline/upstream/third-party/argo/vendor/workflow-controller-rbac-cluster/kustomization.yaml
applications/pipeline/upstream/third-party/argo/vendor/workflow-controller-rbac-namespace/kustomization.yaml

步骤 3：改 kustomization 指向本地#

修改下面 4 个文件，把每个 https://github.com/argoproj/argo-workflows/...?ref=v3.7.3 替换成本地相对路径：

3.1 applications/pipeline/upstream/third-party/argo/base/kustomization.yaml

 resources:
-- https://github.com/argoproj/argo-workflows/manifests/base/workflow-controller?ref=v3.7.3
+- ../vendor/workflow-controller

3.2 applications/pipeline/upstream/third-party/argo/installs/cluster/kustomization.yaml

 resources:
-- https://github.com/argoproj/argo-workflows/manifests/base/crds/minimal?ref=v3.7.3
-- https://github.com/argoproj/argo-workflows/manifests/cluster-install-no-crds/workflow-controller-rbac?ref=v3.7.3
+- ../../vendor/crds-minimal
+- ../../vendor/workflow-controller-rbac-cluster
 - ../../base

3.3 applications/pipeline/upstream/third-party/argo/installs/namespace/kustomization.yaml

 resources:
-- https://github.com/argoproj/argo-workflows/manifests/namespace-install/workflow-controller-rbac?ref=v3.7.3
+- ../../vendor/workflow-controller-rbac-namespace

3.4 applications/pipeline/upstream/third-party/argo/installs/namespace/cluster-scoped/kustomization.yaml

 resources:
-- https://github.com/argoproj/argo-workflows/manifests/base/crds/minimal?ref=v3.7.3
+- ../../../vendor/crds-minimal

步骤 4：本地验证 kustomize build 通过#

kustomize build applications/pipeline/upstream/third-party/argo/installs/cluster >/dev/null && echo OK
kustomize build my-kubeflow/pipeline >/dev/null && echo OK

两条都输出 OK 即代表 Pipeline vendor 化完成，可以进入下面的部署流程。

配置 kubeflow 部署节点#

Kubeflow 控制面组件需要固化运行在专用 infra 节点（ai-modeltrain-prod-kworker-01/02/03-cpu），与 GPU 业务节点、control-plane 节点隔离。

方案原理：给三台节点打 NoSchedule taint，组件 wrapper 通过 Kustomize Component 统一注入对应 toleration；用户业务负载（Notebook、TrainJob、InferenceService 等）不带此 toleration，调度器自动将其排除到 GPU 节点池。

节点打标与 taint（IaC 维护，节点初始化时执行）：

# label：语义标识（非调度必需）
kubectl label node ai-modeltrain-prod-kworker-0{1,2,3}-cpu \
  scclabs.dev/node-pool=kubeflow-node

# taint：排他性保障（核心）
kubectl taint node ai-modeltrain-prod-kworker-0{1,2,3}-cpu \
  scclabs.dev/node-pool=kubeflow-node:NoSchedule

前置依赖：

  • GPU 节点必须带 taint（如 nvidia.com/gpu=present:NoSchedule，由 GPU Operator 默认打）
  • control-plane 节点必须带 taint（如 node-role.kubernetes.io/control-plane:NoSchedule，kubeadm 默认打）

确认命令：

kubectl get nodes -o json | jq -r '.items[] | "\(.metadata.name): \(.spec.taints // [])"'

所有部署命令均通过 my-kubeflow/ 下的 wrapper 完成 toleration 注入，upstream 的 common/ 和 applications/ 文件保持原样不修改。

前置依赖：MetalLB（用于暴露 Kubeflow UI）#

Kubeflow UI 通过 LoadBalancer Service 暴露，依赖 MetalLB 分配 VIP。my-kubeflow/istio wrapper 会把 istio-ingressgateway Service 改回 LoadBalancer 类型，并通过 MetalLB 注解固定到 VIP 10.81.215.101。

部署 Kubeflow 前确认：

# 1. MetalLB 已部署
kubectl get pods -n metallb-system

# 2. IPAddressPool 包含 10.81.215.101
kubectl get ipaddresspools -n metallb-system -o yaml | grep -A2 addresses

# 3. 目标 VIP 10.81.215.101 未被占用
kubectl get svc -A -o jsonpath='{range .items[*]}{.status.loadBalancer.ingress[*].ip}{"\n"}{end}' \
  | sort -u | grep 10.81.215.101
# 无输出即可用

未部署 MetalLB 参考 network/metallb/README.md。

如需更换 VIP，修改 community-distribution-26.03/my-kubeflow/istio/kustomization.yaml 里 metallb.universe.tf/loadBalancerIPs 的值，重新 kubectl apply -k my-kubeflow/istio 即可。

前置依赖：StorageClass#

Kubeflow 内部 3 个有状态服务需要持久化存储：

PVC 组件 用途 大小

mysql-pv-claim KFP Pipeline 元数据库 20Gi

upstream 的 PVC 没指定 storageClassName，集群无 default SC 时 PVC 会一直 Pending。my-kubeflow/katib 和 my-kubeflow/pipeline wrapper 已通过 patch 显式注入 storageClassName: shared-gpfs。

部署前确认 SC 可用：

kubectl get sc shared-gpfs
# 期望：PROVISIONER=spectrumscale.csi.ibm.com，STATUS 为 Bound 时立即就绪

如需改用其他 SC（如 local-path、其他 CSI 驱动等）：

修改下面两个文件里的 storageClassName 字段（共 3 处）：

  • community-distribution-26.03/my-kubeflow/katib/kustomization.yaml
  • community-distribution-26.03/my-kubeflow/pipeline/kustomization.yaml

然后重新 apply：

kubectl apply -k my-kubeflow/katib
kubectl apply -k my-kubeflow/pipeline

⚠️ PVC 已创建后 storageClassName 不可变。如果之前已经 apply 过、PVC 处于 Pending 状态，需要先删 PVC 再 apply：

kubectl delete pvc -n kubeflow katib-mysql mysql-pv-claim seaweedfs-pvc

Istio （必须）#

  • 检查 cilium 是否符合配置要求，必须满足一下输出配置，理由如下

    设置 bpf-lb-sock-hostns-only=true 后，Cilium socket LB 只在 host namespace 生效，不会干扰 Istio sidecar，安全性更高；缺少 bpf-lb-sock-hostns-only: "true"，这会导致 Istio sidecar 流量重定向被 Cilium 的 socket load balancing 干扰，从而出现 RBAC access denied on the central dashboard 或其他 Kubeflow 组件通信问题。

    cilium 配置

(base) ➜  ~ kubectl get configmaps -n kube-system cilium-config -o yaml | grep -E 'bpf-lb-sock-hostns-only|cni-exclusive'
  bpf-lb-sock-hostns-only: "true"
  cni-exclusive: "false"
  • 部署 istio。my-kubeflow/istio/ 已包含 allow-host-remote-node-to-gateways.yaml：放行 cilium reserved host / remote-node identity 到 ingressgateway，否则跨节点 LB / NodePort 流量会被 NetworkPolicy default-deny 丢弃（症状：port-forward 通、LB VIP 不通；详见 troubleshooting/2026-06-18-lb-vip-unreachable-final.md）。
kubectl apply -k my-kubeflow/istio/crds
kubectl wait --for=condition=Established --timeout=60s \
  crd/authorizationpolicies.security.istio.io \
  crd/gateways.networking.istio.io \
  crd/sidecars.networking.istio.io
kubectl apply -k my-kubeflow/istio/namespace
kubectl apply -k my-kubeflow/istio
kubectl wait --for=condition=Ready pods --all -n istio-system --timeout 180s

Kubeflow Pipelines（KFP 2.16.x）在 26.03 版本提供了两种完全不同的后端存储方式，选择取决于你的运维偏好和 GitOps 程度。

维度 传统 Database 模式（推荐大多数用户） Kubernetes Native API 模式（GitOps 友好）
Pipeline 定义存储 MySQL/PostgreSQL 外部数据库 Kubernetes CR（Pipeline / PipelineVersion）
安装命令 ./tests/pipelines_install.sh kustomize build applications/pipeline/upstream/env/cert-manager/platform-agnostic-multi-user-k8s-native
适用场景 传统 UI + SDK 使用、生产多租户 强 GitOps、声明式管理、CI/CD 流水线
优势 成熟、功能最全、UI 体验最佳 原生 K8s 工具（kubectl、Argo CD）、无外部 DB 依赖
劣势 需要维护数据库、备份较复杂 部分高级功能仍在完善、迁移成本
Artifact Store 默认 SeaweedFS（S3 兼容，替代老 MinIO） 同左，所有 overlay 已切换
多用户支持 原生支持（Profiles + RBAC） 支持，但需注意 Admission Webhook

默认 Artifact Store 变化：所有 overlay 现在统一使用 SeaweedFS 作为 S3 兼容对象存储（替换 MinIO）。它负责存储 Pipeline 运行时的 artifacts（模型、数据、中间结果）。SeaweedFS 更轻量、高可用。

部署完成后，istio-ingressgateway 已通过 MetalLB 分配 LoadBalancer VIP（10.81.215.101）。

1. 确认 VIP 已分配

kubectl get svc istio-ingressgateway -n istio-system
# EXTERNAL-IP 列应为 10.81.215.101

2. 浏览器访问

  • URL: https://staii.seres.cn
  • 账号密码：见 my-kubeflow/dex/dex-config-patch.yaml 的 staticPasswords（user01@example.com）

临时调试方案：port-forward（仅 master 本机调试 / MetalLB 故障时备用）

# --address 0.0.0.0 让其他机器可通过 master 节点 IP 访问；
# 默认 127.0.0.1 只能在 master 本机访问。
# 生产请走上面的 LoadBalancer VIP，port-forward 仅作临时调试。
kubectl port-forward svc/istio-ingressgateway -n istio-system \
  --address 0.0.0.0 8080:80
  • master 本机：http://localhost:8080
  • 同网段机器：http://<master-node-ip>:8080

⚠️ --address 0.0.0.0 监听所有网卡，仅在受信网络使用，否则改回默认 127.0.0.1 + SSH 隧道：ssh -L 8080:localhost:8080 <user>@<master>。
