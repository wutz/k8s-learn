Kueue#

Kubernetes 批处理队列管理器，提供配额控制、公平分配和优先级抢占。

与 scheduler-plugins Coscheduling 的关键区别：Kueue 在准入层做 Gang 判断（资源够才创建 Pod），而非在调度层逐个尝试。资源不足时零 Pod、零调度开销。

部署#

1. 安装 Kueue（controller + webhook + CRD）#

helmwave up --build

验证 Pod Running：

kubectl get pods -n kueue-system

2. 创建队列基础设施（必须）#

helmwave 只部署 Kueue 本身，不创建队列资源。以下资源是 Kueue 正常运行的必要前提：

顺序 资源 说明
1 Topology TAS 拓扑层级（单层 hostname）
2 ResourceFlavor GPU 节点池标签（按 scclabs.dev/gpu 区分型号）+ TAS 引用
3 ClusterQueue 集群级配额池（引用 ResourceFlavor）
4 LocalQueue namespace 级入口（引用 ClusterQueue）
— WorkloadPriorityClass 可选，Workload 级优先级（独立于 Pod PriorityClass）

⚠️ 应用前必须修改 queue-setup.yaml 中的 nominalQuota：Kueue 不自动发现集群资源，配额必须手工填写。文件中当前值是测试集群的（3×8=24 GPU），换集群需替换。

获取集群 allocatable 汇总：

./get-quota.sh              # 所有 GPU 节点（node-role.kubernetes.io/gpu）
./get-quota.sh rtx-5090     # 仅 rtx-5090 节点池（按 ResourceFlavor 分别统计）

nominalQuota 应填 allocatable（不是 capacity）—— allocatable = capacity − kubelet system reservation，是 Pod 实际可用的上限。

修改完成后 apply：

kubectl apply -f queue-setup.yaml

# 验证 ClusterQueue active（status 应显示 True）
kubectl get clusterqueue gpu-cluster-queue

# 验证 LocalQueue
kubectl get localqueue gpu-local-queue -n default

3. TrainJob 使用 Kueue#

TrainJob 接入 Kueue 只需 加 1 个 label + 设 suspend: true：

apiVersion: trainer.kubeflow.org/v1alpha1
kind: TrainJob
metadata:
  name: my-job
  labels:
    kueue.x-k8s.io/queue-name: gpu-local-queue       # 必填：指向 LocalQueue
    kueue.x-k8s.io/priority-class: low-priority      # 可选：Workload 优先级
spec:
  suspend: true                                      # Kueue 控制 unsuspend
  runtimeRef:
    name: torch-distributed
  trainer:
    numNodes: 1
    resourcesPerNode:
      requests:
        nvidia.com/gpu: "1"
      limits:
        nvidia.com/gpu: "1"

Label 说明：

Label 必填 用途
kueue.x-k8s.io/queue-name ✅ 指向 LocalQueue。缺失则 Kueue 不接管，TrainJob 永远 Suspended
kueue.x-k8s.io/priority-class ❌ Workload 级优先级，决定排队顺序与抢占行为。可选值（见 queue-setup.yaml）：high-priority (10000) / low-priority (1000)。不设则默认 0（最低）

⚠️ 不要设 spec.managedBy — 该字段仅用于 MultiKueue（跨集群）。单集群 Kueue 走 webhook + queue-name label 路径，设 managedBy 会被 Trainer webhook 拒绝。

完整示例参考 ai/trainer/examples/*/kueue/。

附录：TAS 双门控原理#

一线工程师排障时如果遇到"配额够但 Workload 不被 Admit"，看这一节。

准入双门控（源码 clusterqueue_snapshot.go Fits()）#

启用 TAS（ResourceFlavor 设置 topologyName）后，Workload 准入受 两个独立门控 控制，取更严格者：

门控 类型 来源 维护方式
门 1：nominalQuota 静态配额上限 ClusterQueue 配置 手工填写，节点变化不感知
门 2：TAS freeCapacity 动态节点容量 实时扫描节点 allocatable 自动感知，节点增减立即生效

实际行为：

  • 两门都通过 → Admit，Pod 创建
  • 任一门不通过 → 排队（Workload QuotaReserved=False 或 Admitted=False）

TAS freeCapacity 计算（源码 tas_flavor_snapshot.go）#

freeCapacity = Σ(节点 .status.allocatable) − 非TAS Pod 占用（DaemonSet 等）
              ↑ 仅计入 Ready=True 且 .spec.unschedulable=false 的节点

nominalQuota 设置策略#

设置值 行为 风险
= allocatable 总量（推荐） 两门一致；TAS 失效时 nominalQuota 兜底 无
> allocatable 完全依赖 TAS 门 TAS 失效时无保护
< allocatable nominalQuota 更严格 浪费 TAS 发现的额外容量

关键不可变字段（修改需重建）#

资源 不可变字段
Topology levels
ResourceFlavor（设了 topologyName 后） nodeLabels、tolerations、topologyName

TAS 配置约束#

  • kubernetes.io/hostname 只能用在 Topology 的最低层（最后一层）
  • 所有被 TAS 管理的节点必须有 Topology levels 中的每个 label
  • GPU 节点的 tolerations 必须在 ResourceFlavor 中显式声明（TAS 不感知 webhook 自动注入）

排查 TAS 失败#

# 1. 查 Workload 状态消息（TAS 错误会打印 excluded nodes 与原因）
kubectl get workload <name> -n <ns> -o yaml | yq '.status.conditions'

# 2. 查 ResourceFlavor 是否绑定 Topology
kubectl get resourceflavor rtx-5090 -o yaml | grep topologyName

# 3. 查节点是否带齐 Topology levels 中的所有 label
kubectl get nodes -L kubernetes.io/hostname,scclabs.dev/gpu
