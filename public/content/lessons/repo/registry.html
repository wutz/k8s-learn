Docker Registry#

基于 Docker Registry v3 + joxit/docker-registry-ui 的私有镜像仓库部署模板。

本方案是仓库服务的缺省镜像仓库，适合单集群内部使用、账号可控、只需要 push / pull / delete 的场景。

如果需要多项目隔离与 RBAC、上游镜像代理缓存 (proxy cache)、漏洞扫描或跨机房复制，改用备选方案 Harbor。两者部署其一即可，选型对比见 仓库服务。

注意#

  • 当前模板已启用 Docker Registry 原生 htpasswd Basic Auth。部署前必须先创建 registry/registry-auth Secret。
  • Basic Auth 只做账号验证，不做项目级或读写权限区分。已登录账号默认可 pull / push / delete。
  • 账号密码认证必须配合 TLS 使用。LoadBalancer 明文 HTTP 只适合隔离可信内网或临时测试。
  • 当前 registry 开启删除能力，UI 也允许删除镜像。账号泄露后影响较大，需要控制账号分发。
  • 大镜像经 Ingress 上传/下载时，还需要检查 Ingress 网关的 body size、连接超时和空闲超时。

访问方式(二选一)#

  • LoadBalancer: 使用 deploy/loadbalancer/
    • 默认 registry 地址是 192.168.3.111:5000
    • 默认 UI 地址是 192.168.3.112:80
    • 适合可信内网 IP 直连
    • 客户端走明文 HTTP 时，Docker / containerd 可能需要配置 insecure registry
  • Ingress + TLS: 使用 tls/ + deploy/ingress/
    • 默认域名是 cr.example.com
    • 入口是 https://cr.example.com
    • registry / UI Service 是 ClusterIP，不分配 LoadBalancer IP
    • 适合只允许 HTTPS 域名入口的环境

如果现场确实需要同时保留 LoadBalancer 和 Ingress，见“高级场景：同时保留 IP 和域名入口”。默认不需要。

关键配置#

存储#

  • 修改 deploy/base/pvc.yaml 中的 resources.requests.storage 配置: 仓库存储容量，模板默认 10Ti
    • 空间不足会导致镜像 push 失败
  • 修改 deploy/base/pvc.yaml 中的 accessModes 配置: 模板默认 ReadWriteMany
    • 多副本 registry 需要共享存储
    • 如果现场只有 RWO 存储，需要把 registry 副本数改成 1
  • 修改 deploy/base/pvc.yaml 中的 storageClassName 配置: 模板默认 shared-nfs
    • 需要替换成现场集群实际可用的 StorageClass
    • StorageClass 不存在或不支持 RWX 时，PVC/Pod 会卡住

registry#

  • 修改 deploy/base/deployment.yaml 中的 replicas 配置: 模板默认 3
    • 只有确认共享存储支持多节点并发读写时，才保留多副本
  • 修改 deploy/base/deployment.yaml 中的 REGISTRY_HTTP_SECRET 配置: 多副本必须保持一致
    • 当前模板直接写在 manifest 中
    • 正式落地建议改成 Secret 引用
  • 准备 registry/registry-auth Secret: registry 启动时会挂载 /auth/htpasswd
    • Secret 缺失会导致 registry Pod 无法启动
    • htpasswd 必须使用 bcrypt 格式生成，即 htpasswd -Bbn
    • 不要把真实 htpasswd 文件提交进仓库
  • 确认 deploy/base/deployment.yaml 中的 REGISTRY_STORAGE_DELETE_ENABLED 配置: 模板默认 true
    • 开启后允许删除镜像 manifest
    • 已登录账号默认具备删除能力，账号分发要收敛

LoadBalancer 入口#

  • 修改 deploy/loadbalancer/service.yaml 中的 metallb.universe.tf/loadBalancerIPs 配置: registry 的 LoadBalancer IP，模板默认 192.168.3.111
  • 修改 deploy/loadbalancer/ui-service.yaml 中的 metallb.universe.tf/loadBalancerIPs 配置: UI 的 LoadBalancer IP，模板默认 192.168.3.112
  • 确认 deploy/loadbalancer/service.yaml 中的 sessionAffinity 配置: 模板默认 ClientIP
    • 大镜像上传时建议保留

Ingress + TLS 入口#

  • 修改 deploy/ingress/ingress.yaml 中的 host 配置: 模板默认 cr.example.com
  • 修改 deploy/ingress/ingress.yaml 中的 ingressClassName 配置: 模板默认 istio
    • 如果现场不是 Istio Ingress，需要替换成实际 IngressClass
  • 修改 deploy/ingress/ingress.yaml 中的 tls.secretName 配置: 模板默认 registry-ingress
    • 需要和 tls/kustomization.yaml 中生成的 Secret 名字一致
    • 当前模板使用 Istio Ingress，TLS Secret 会创建到 istio-system namespace，供 istio-ingressgateway 加载
  • 准备 Ingress TLS 证书: Secret 名字默认 registry-ingress
    • 生产环境需要提前向证书管理员或企业 CA 申请正式证书
    • 正式证书文件放到 tls/tls.crt 和 tls/tls.key
    • 证书 SAN 必须覆盖 Ingress host，例如 cr.example.com
    • tls/gen-cert.sh 只用于生成自签证书，适合测试或临时验证，不作为生产证书流程

账号 Secret#

部署 registry 前先创建 registry-auth Secret：

USER_NAME='<用户名>'
USER_PASS='<密码>'

htpasswd -Bbn "$USER_NAME" "$USER_PASS" > /tmp/registry-htpasswd

kubectl create namespace registry --dry-run=client -o yaml | kubectl apply -f -
kubectl -n registry create secret generic registry-auth \
  --from-file=htpasswd=/tmp/registry-htpasswd \
  --dry-run=client -o yaml | kubectl apply -f -

rm -f /tmp/registry-htpasswd

说明：

  • 本机需要有 htpasswd 命令；macOS 默认路径通常是 /usr/sbin/htpasswd。
  • -B 表示生成 bcrypt 格式，Docker Registry 认证必须使用该格式。
  • Secret key 必须叫 htpasswd，Deployment 会挂载为 /auth/htpasswd。

LoadBalancer#

1. 部署#

kubectl apply -k deploy/loadbalancer/

兼容旧命令：kubectl apply -k deploy/ 当前也会部署 LoadBalancer 模式。

2. 验证#

kubectl get pod,svc -n registry
curl -v http://192.168.3.111:5000/v2/
curl -v -u '<用户名>:<密码>' http://192.168.3.111:5000/v2/

预期：

  • 不带账号访问 /v2/ 返回 401 Unauthorized。
  • 带正确账号访问 /v2/ 返回 200 OK。

3. 使用仓库#

docker login 192.168.3.111:5000
docker tag alpine:latest 192.168.3.111:5000/library/alpine:latest
docker push 192.168.3.111:5000/library/alpine:latest
docker pull 192.168.3.111:5000/library/alpine:latest

如果客户端走明文 HTTP，Docker / containerd 可能需要配置 insecure registry。生产环境优先使用 Ingress + TLS。

Ingress + TLS#

1. 准备 TLS Secret#

生产环境先准备正式证书：

# 从证书管理员或企业 CA 提前申请，证书 SAN 必须覆盖 cr.example.com
cp <正式证书.crt> tls/tls.crt
cp <正式证书.key> tls/tls.key
kubectl apply -k tls/

测试或临时验证可以生成自签证书：

export DOMAIN=cr.example.com
./tls/gen-cert.sh
kubectl apply -k tls/

说明：

  • tls/gen-cert.sh 生成的是自签名证书，只适合测试环境或临时连通性验证。
  • 生产环境不要直接使用自签证书，需要提前申请正式证书并保存为 tls/tls.crt 和 tls/tls.key。
  • kubectl apply -k tls/ 会创建 istio-system/registry-ingress TLS Secret。
  • 当前模板使用 ingressClassName: istio。实测 Istio ingressgateway 从 istio-system namespace 加载 TLS credential；Secret 放在 registry namespace 会导致 443 握手 reset。
  • tls/tls-secret.yaml 只是手工创建 Secret 的模板，不要直接 apply。

2. 部署 Ingress 模式#

kubectl apply -k deploy/ingress/

Ingress 规则：

  • /v2 → registry:5000
  • / → registry-ui:80
  • ingressClassName → istio
  • TLS Secret → registry-ingress

3. 验证#

kubectl get pod,svc,ingress -n registry
curl -vk https://cr.example.com/v2/
curl -vk -u '<用户名>:<密码>' https://cr.example.com/v2/

预期：

  • 不带账号访问 /v2/ 返回 401 Unauthorized，并带 WWW-Authenticate: Basic realm="Registry Realm"。
  • 带正确账号访问 /v2/ 返回 200 OK。

4. 使用仓库#

docker login cr.example.com
docker tag alpine:latest cr.example.com/library/alpine:latest
docker push cr.example.com/library/alpine:latest
docker pull cr.example.com/library/alpine:latest

高级场景：同时保留 IP 和域名入口#

默认不需要这个模式。只有现场明确要求同时保留 192.168.3.111:5000 和 https://cr.example.com 时再使用。

先部署 LoadBalancer：

kubectl apply -k deploy/loadbalancer/

再准备 TLS Secret：

cp <正式证书.crt> tls/tls.crt
cp <正式证书.key> tls/tls.key
kubectl apply -k tls/

最后只追加 Ingress 对象：

kubectl apply -f deploy/ingress/ingress.yaml -n registry

这个命令只创建 Ingress，不会把已有 LoadBalancer Service 改成 ClusterIP。

配置说明#

deploy/base/config.yml#

  • http.addr: :5000: registry 监听端口
  • http.net.readtimeout / writetimeout: 大镜像传输超时
  • storage.filesystem.rootdirectory: 镜像数据目录
  • storage.delete.enabled: true: 允许删除镜像
  • http2.maxconcurrentstreams: 只有 TLS 场景才更有意义，纯 HTTP 下不要指望 h2c

deploy/base/deployment.yaml#

  • image: registry:3.0.0
  • 挂载 config.yml
  • 挂载 registry-auth Secret 到 /auth/htpasswd
  • 挂载 PVC 到 /var/lib/registry
  • REGISTRY_AUTH=htpasswd: 启用 Docker Registry 原生 Basic Auth
  • REGISTRY_AUTH_HTPASSWD_PATH=/auth/htpasswd: 读取账号密码文件
  • REGISTRY_HTTP_SECRET 当前硬编码在 manifest 中；正式落地建议改为 Secret 引用

deploy/base/ui-deployment.yaml#

  • NGINX_PROXY_PASS_URL 默认指向 http://registry:5000
  • 如果改 Service 名称，要同步改这里
  • DELETE_IMAGES=true 会允许通过 UI 删除镜像；已登录账号可执行删除操作

deploy/loadbalancer/service.yaml / deploy/loadbalancer/ui-service.yaml#

  • LoadBalancer 模式使用这两个 Service
  • 高级共存场景也复用这两个 Service

deploy/ingress/service-clusterip.yaml / deploy/ingress/ui-service-clusterip.yaml#

  • Ingress + TLS 模式使用这两个 ClusterIP Service
  • 不会分配 LoadBalancer IP

删除镜像#

先取 manifest digest：

digest=$(curl -sI \
  -u '<用户名>:<密码>' \
  -H 'Accept: application/vnd.docker.distribution.manifest.v2+json' \
  http://<registry-url>/v2/<image>/manifests/<tag> \
  | awk -F': ' 'tolower($1)=="docker-content-digest"{print $2}' \
  | tr -d '\r')

echo "$digest"

再删除 manifest：

curl -v -u '<用户名>:<密码>' -X DELETE \
  http://<registry-url>/v2/<image>/manifests/$digest

说明：删除 manifest 后，磁盘空间不会立刻释放，需要再执行安全 GC。

安全垃圾回收#

不要在仍有 push/upload 写入时直接 GC。最小安全流程：

# 1. 先停止写入入口；示例：临时缩容 registry
kubectl scale deploy/registry -n registry --replicas=0

# 2. 启动单副本用于执行 GC
kubectl scale deploy/registry -n registry --replicas=1
kubectl rollout status deploy/registry -n registry

# 3. 执行 GC
pod=$(kubectl get pod -n registry -l app=registry -o jsonpath='{.items[0].metadata.name}')
kubectl exec -n registry "$pod" -- \
  registry garbage-collect /etc/docker/registry/config.yml

# 4. 恢复副本数
kubectl scale deploy/registry -n registry --replicas=3

更稳妥的生产做法是：停止入口流量后，用专门 GC Job 挂载同一个 PVC 执行垃圾回收。

卸载#

LoadBalancer#

kubectl delete -k deploy/loadbalancer/

如果使用旧命令部署，也可以执行：

kubectl delete -k deploy/

Ingress + TLS#

kubectl delete -k deploy/ingress/
kubectl delete -k tls/

高级共存场景#

kubectl delete -f deploy/ingress/ingress.yaml -n registry
kubectl delete -k tls/
kubectl delete -k deploy/loadbalancer/

如果 PVC 需要保留镜像数据，删除前先确认存储回收策略。
